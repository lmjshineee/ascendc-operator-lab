# 性能评测与优化方案

## 1. 先固定可比较的基线

每个算子先保存一个正确的单核/固定 tile 基础实现，再增加多核、tile 调整和可选双缓冲。题目允许对基础实现或 CANN 内置算子比较；若内置调用尚未接入，先以同设备基础实现作为基线，明确命名，不能写成“超越 CANN”。

相同 shape、dtype、布局、数据和输出语义；尽量一致的调用路径。若一方经框架而另一方直调，分别报告设备 kernel 时间和含调用开销的端到端时间，不能混用计算 speedup。

## 2. 计时流程

1. 固定随机种子、输入与环境；先运行正确性比较，失败的 case 禁止计入性能结论。
2. 编译、注册、分配、数据准备放到计时外；如测端到端则列出包含项。
3. 建议先预热 20 次，观察是否稳定；然后至少 5 组，每组 100 次，按实际延迟调整数量并记录。
4. NPU 通常异步执行，不能只测 Host 提交时间。使用对应版本支持的设备 event/profiler，或清楚标注同步后的 Host elapsed。每段计时必须等待被测任务完成。
5. 保存每组原始时延；报告 median 和 P90、最小值、样本数。若一次计时覆盖 K 次调用，只能说该组均摊时间，不能把它当 K 个独立延迟样本。
6. 同一设备上交替测基线和优化，记录其他负载、频率/功耗状态（可获取时）及 profiler 自身开销。多次重跑确认改善不是噪声。

## 3. 单变量消融

| 假设 | 只改变什么 | 观察什么 | 可能失败原因 |
|---|---|---|---|
| 大 Add 可从更多核受益 | cores | 延迟、有效带宽、规模拐点 | 小输入启动开销、带宽饱和 |
| tile 太小搬运开销高 | tile_elems | 延迟、搬运次数、UB 占用 | tile 太大挤占缓冲/临时区 |
| 双缓冲能覆盖部分搬运 | buffer_count=1/2 | 时间线重叠、总时延 | 计算太短或空间不足 |
| Softmax 按行分配有规模拐点 | rows_per_core 或核数 | 不同行数/行宽的延迟 | 行数太少、负载不均、归约成本 |

各参数候选从实际设备支持范围和 UB 预算推导，不硬编码一个型号的核数/容量。保留表现不佳的配置。若用某些形状调参，再用保留形状做验证，避免只展示“最佳案例”。

## 4. 指标与结论

`speedup = baseline_median_us / optimized_median_us`；小于 1 是变慢。Add 可估算 `effective_GB_s = 3*N*d / (time_us*1000)`，只表示理想必要字节数除以所测时间，不等于实际总线流量或硬件峰值利用率。

单算子加速不能直接推成模型吞吐提升、TTFT 或 P99 改善。先说明支持形状、dtype、设备与测量边界，再给结论。优化至少记录“改动→假设→实验→证据→结论→局限”。

原始记录字段见 `benchmarks/record.example.json`，其中 null 全是待填字段，不是零时延。性能采集器属于设备阶段 TODO，初始化仓库没有虚构跑分。
